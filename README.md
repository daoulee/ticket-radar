# Ticket Radar

### 공연을 찾는 순간부터, 거래 조건을 확인하는 순간까지.

티켓레이더는 공연을 찾고 티켓을 예매하거나 양도받는 과정을 한곳에서 살펴볼 수 있도록 만든 공연 티켓 중개 서비스 프로젝트입니다. 공연 정보와 거래 조건을 더 쉽게 확인할 수 있는 경험을 고민했습니다.

[웹 시연 보기](https://ticketradar.month32.workers.dev/) · [기획과 범위](PLAN.md) · [개발 기록](Communicate.md) · [할 일](TODO.md)

> **현재는 시연 단계입니다.** 공개 웹의 예매·좌석·매물은 가상 데이터이며, 토스페이먼츠는 테스트 환경을 사용합니다. 실제 금전 이동, 좌석 예약, 티켓 발급은 이뤄지지 않습니다. 공개 웹의 **공통 거래**와 iPhone D2 시뮬레이터에 새로 설치한 Expo 앱은 같은 계정·거래 서버를 사용하도록 연결했습니다. 실제 계정으로 양쪽 거래 완료까지 확인하는 검증은 남아 있습니다.


공통 거래의 웹 로그인은 HttpOnly·Secure 쿠키로 유지되며 서버에서 세션을 확인합니다. 기존 탭에 있던 로그인 정보는 서버 검증에 성공하면 쿠키로 옮기고 탭 저장소에서 제거합니다.

## 어떤 문제에서 시작했나요?

공연 하나를 보려고 해도 공연 일정과 장소, 티켓 가격, 양도 조건, 입장 규정을 여러 곳에서 따로 확인해야 합니다. 판매글의 가격이 기준 가격과 맞는지, 전달 방식에 주의할 점은 없는지도 이용자가 직접 살펴봐야 합니다.

우리는 이 과정을 조금 더 단순하게 만들고 싶었습니다. **공연 정보와 티켓 거래 흐름을 한 화면에서 이어 주고, 거래 전에 확인할 정보를 보여 주는 것**이 티켓레이더의 출발점입니다.

## 어떻게 풀었나요?

| 이용자가 하는 일 | 티켓레이더에서 제공하는 경험 |
| --- | --- |
| 공연 찾기 | KOPIS 공연 목록을 살펴보고 공연 정보 확인 |
| 티켓 살펴보기 | 가격과 좌석, 전달 조건을 확인하는 예매·양도 시연 |
| 거래 전 확인 | 판매글의 정보와 등록된 공식 안내를 비교해 확인할 사항 표시 |
| 구매 과정 체험 | 가상 대기·좌석 선택과 토스페이먼츠 테스트 결제 경험 |

이 프로젝트는 티켓의 진위나 입장 가능 여부를 보증하거나 불법 여부를 확정하지 않습니다. 공연사와의 제휴 판매나 신고 기관 자동 연계도 현재 완료된 기능이 아닙니다.

제보함은 담당자 권한을 다시 정비하는 동안 공개 공통 서버에서 준비 중으로 표시합니다. 시연용 담당 계정이 실제 주최 측 인증을 뜻하지는 않습니다.

## 무엇으로 만들었나요?

| 영역 | 기술 | 역할 |
| --- | --- | --- |
| 웹 | React, TypeScript, Vite | 공연 탐색과 거래 시연 화면 |
| 앱 | React Native, Expo, TypeScript | 모바일 공연 탐색·회원가입·거래 화면 |
| 서버 | Node.js, TypeScript | 계정, 거래 규칙, 외부 API 연동 |
| 데이터 검증 | Zod | 웹·앱·서버 사이의 데이터 형식 확인 |
| 외부 서비스 | KOPIS API, Gmail SMTP·Gmail API, 토스페이먼츠 테스트 환경 | 공연 목록, 인증 메일, 테스트 결제 |
| 배포·검증 | Cloudflare Workers, Vitest, Jest, Playwright | 공개 웹과 자동화 테스트 |

화면, 거래 규칙, 외부 데이터 접근을 나눠 각 부분을 따로 확인할 수 있도록 구성했습니다. KOPIS 조회가 일시적으로 실패하면 제한된 횟수로 재시도하고, 계속 실패하면 이용자에게 오류를 보여 줍니다. 거래 가격은 확인 가능한 기준가와 판매자가 입력한 원구매가를 기준으로 검사하며, 입력한 원구매가 자체의 진위는 검증하지 않습니다.

테스트 결제는 서버가 시연 주문 금액과 승인 응답을 확인합니다. 비밀번호는 서버에서 `scrypt`로 해시하고, API 비밀키는 코드나 앱 화면에 넣지 않도록 관리했습니다.

## AI와 함께 개발한 방법

이 프로젝트는 팀이 해결할 문제와 시연 범위를 정하고, AI 도구를 활용해 기획·구현·검토를 반복하는 방식으로 진행했습니다. AI가 제안한 결과를 그대로 완성으로 보지 않고, 사람이 화면을 확인하고 요구사항에 맞게 조정했습니다.

1. **작게 나누기** — 하나의 사용자 흐름이나 오류를 기준으로 작업 범위와 담당 파일을 정했습니다.
2. **맥락 전달하기** — 기존 코드, 명세와 협업 기록을 먼저 확인한 뒤 AI에 입력과 기대 결과를 전달했습니다.
3. **만들고 확인하기** — 코드와 화면을 만들고 자동 테스트, 브라우저, iPhone 시뮬레이터에서 확인했습니다.
4. **피드백으로 고치기** — 팀원 QA에서 발견한 공연 목록 오류처럼 재현 조건을 확인하고 수정·재검증했습니다.

여기서 말하는 바이브 코딩은 요구사항을 자연어로 설명하고 AI와 빠르게 반복하는 개발 방식입니다. 결과를 이해하고 판단하는 책임은 팀에 두었습니다. 개발에 사용한 AI 도구와 제품 안에서 동작하는 AI 기능은 별개로 구분합니다.

### 작업에 참고한 스킬

스킬은 AI 개발 도구가 특정 작업을 할 때 참고하는 지침입니다. 설치된 스킬 전체를 실제 사용한 것으로 간주하지 않고, 작업 기록에서 활용이 확인된 사례를 적었습니다.

| 스킬 | 프로젝트에서 활용한 내용 |
| --- | --- |
| `frontend-design` | 웹 예매 화면의 구성과 안내 문구 정리 |
| `expo-native-ui`, `expo-ui` | 앱 구매 확인·좌석 선택 화면의 구성과 조작 방식 검토 |
| `imagegen` | 실제 공연과 혼동하지 않도록 가상 공연 포스터 제작 |
| `debugging-and-error-recovery` | KOPIS 목록 오류 재현, 원인 범위 좁히기, 재검증 |

프로젝트에 등록된 스킬 목록과 출처는 [개발 스킬 안내](docs/APM_SKILLS.md)에서 확인할 수 있습니다.

## 직접 실행하기

> 아래 명령은 이 저장소의 구성 기준입니다. 일부 기능은 설정과 배포 여부에 따라 다르게 동작합니다. Node.js 24 이상과 npm이 필요합니다.

**모바일 PWA**

프로젝트 루트에서 정적 서버를 실행한 뒤 `http://127.0.0.1:5181`을 열어 확인할 수 있습니다.

```bash
python3 -m http.server 5181 --directory mobile-pwa/public
```

**웹 시연**

```bash
cd shared && npm ci
cd ../web && npm ci
npm run dev
```

**로컬 서버**

```bash
cd shared && npm ci
cd ../server && npm ci
npm start
```

**앱**

```bash
cd shared && npm ci
cd ../mobile && npm ci
npx expo start
```

앱에서 실제 로컬 서버를 사용하려면 실행 환경에 맞는 API 주소와 서버 설정이 필요합니다. 시뮬레이터의 `127.0.0.1`과 실제 휴대전화의 `127.0.0.1`은 같은 주소가 아닙니다. 이메일·외부 API 키는 서버 환경에서만 설정하고 저장소에 올리지 않습니다. 자세한 설정과 테스트는 [서버](server/README.md), [웹](web/README.md), [앱](mobile/README.md) 안내를 참고해 주세요.

Gmail API 발송 연동은 현재 Google OAuth의 **외부 사용자·테스트** 상태입니다. 이 상태에서 발급한 Gmail 발송 권한의 갱신 토큰은 **7일 후 만료**되므로, 만료되면 발신 계정으로 다시 권한을 승인하고 서버의 비밀 설정을 갱신해야 합니다. 공개 공통 서버에서 네이버 주소로 인증 메일이 도착하는 것을 확인했습니다. 안정적인 운영을 위해서는 테스트 상태를 벗어나는 방법과 Google의 앱 확인 요건을 별도로 검토해야 합니다. [Google OAuth 토큰 만료 안내](https://developers.google.com/identity/protocols/oauth2#expiration)
